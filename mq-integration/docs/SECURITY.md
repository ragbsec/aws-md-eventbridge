# Security — IBM MQ <-> EventBridge integration

> **Not yet run on a live stack.** The controls below are read from the
> Terraform, MQSC and compose files as written; verify them with
> `scripts/verify.sh` and a first deploy. This is a **lab**, not a hardened
> production MQ deployment.

## 1. Threat model

| Threat / asset | Control in this lab | Residual risk / note |
|---|---|---|
| Remote login to the host | **No SSH**, no key pair, no port 22 rule. Access is SSM Session Manager only (`AmazonSSMManagedInstanceCore`) | Anyone with `ssm:StartSession` on the instance is effectively root; restrict via IAM and enable session logging |
| Network exposure of MQ / console | **No inbound SG rules by default.** `mq_client_cidrs` / `console_cidrs` are empty; rules exist only if you set them. Docker publishes 1414 and 9443 on `127.0.0.1` (`MQ_BIND_ADDR` default) | Setting both an SG rule and `MQ_BIND_ADDR=0.0.0.0` exposes plaintext MQ (see TLS gap). Never open to `0.0.0.0/0` |
| Anonymous or wrong-user MQ client | `EB.AUTHINFO` (IDPWOS) with `CHCKCLNT(REQUIRED)`; `CHLAUTH('*')` default deny; `USERMAP` allows only `app` on `APP.SVRCONN`; `BLOCKUSER('*MQADMIN')` on the channel | Passwords are OS-user passwords inside the container |
| Over-privileged app identity | `AUTHREC` gives group `mqclient` only `CONNECT` on QM1 and `PUT,GET,INQ,BROWSE` on `ORDERS.**`. The `admin` user (group `mqm`) is for the console only | IBM's `10-dev.mqsc` also creates `DEV.*` objects with their own auth; remove them if you want a minimal surface |
| Instance role abuse | Inline policy: `events:PutEvents` on **one bus ARN**; SQS receive/delete/attributes/visibility on **one queue**; Secrets Manager get/put/describe on **one secret**; `s3:GetObject` on **one object key**; bus CMK use only with `kms:ViaService = events.<region>.amazonaws.com` (only if the bus has a CMK) | `secretsmanager:PutSecretValue` is granted so first boot can populate the secret; this also lets a compromised host overwrite it |
| Credential theft via IMDS | IMDSv2 required (`http_tokens = required`). `http_put_response_hop_limit = 2` | See §2 |
| Secrets in code/state | Secret **container** created by Terraform; values generated by the instance at first boot (`openssl rand`), never in Terraform state, user_data or repo. `.env` and `bridge.env` are written mode 0600 | Compose env vars (`MQ_PASSWORD`, `MQ_*_PASSWORD`) are visible to root via `docker inspect`. `recovery_window_in_days = 0` (lab convenience) means deletion is immediate |
| Loop / event storm | `detail.origin = ibm-mq` stamped on bridge events; `mq-outbound-rule` excludes it | Relies on every other producer not impersonating the origin |
| Message tampering/disclosure in AWS | SQS SSE (SQS-managed key), TLS-only (`aws:SecureTransport`) policies on queues and bundle bucket, S3 public access block, SSE-S3, encrypted gp3 root volume | SQS uses the AWS-managed SQS key, not the platform CMK (see §5) |
| Supply chain | Compose plugin version pinned; MQ image pinned to `icr.io/ibm-messaging/mq:10.0.0.5-r2` (tag exists in icr.io, amd64 only; not yet pulled on a live stack) | Keep it pinned; change only via `mq_image` / `MQ_IMAGE` after testing. Python deps: pin and scan in the bridge image |
| Data on the bus | Order payload only (orderId, product, quantity, amount, timestamp) | Do not put PII or card data in MQ messages bound for the bus (see SECURITY_AND_ONBOARDING §2e) |

## 2. IMDSv2 and why hop limit 2

`http_tokens = required` forces the session-token (IMDSv2) flow, which blocks
the classic SSRF-to-credentials path. The metadata hop limit defaults to 1: the
response packet's TTL is 1, so it reaches a process on the host but **not** a
container behind Docker's bridge network (one extra hop). The `bridge`
container uses the default bridge network and gets AWS credentials from the
instance role, so the limit is set to **2**.

Trade-off: any container (or process in a container) on the host can reach
IMDS and use the role. That is acceptable only because the host runs exactly
the MQ and bridge containers. If you add other workloads, either move to
hop limit 1 with `network_mode: host` for the bridge, or give workloads
separate identities. Setting the limit back to 1 without that change breaks the
bridge with credential errors (`Unable to locate credentials`).

## 3. Secrets handling

1. Terraform creates an empty secret `eb-mq/credentials`.
2. On first boot the instance checks for a value; if absent it generates two 24-character
   alphanumeric passwords and writes `{admin_password, app_password}`; if a value exists it reuses it.
3. It writes `/opt/eb-mq/docker/.env` (0600) for Compose; the bridge reads the
   app password from the compose environment and has `SECRET_ID` for refresh.
4. Rotation: see [`RUNBOOK.md`](RUNBOOK.md) §6. The IBM image applies
   `MQ_*_PASSWORD` when the container starts (unverified: confirm against the image docs), so rotation means recreating the container.
5. Never print the secret in logs or chat. Commands in the cookbook that read
   it pipe it into a variable, never to the terminal.

## 4. TLS on the MQ channel — NOT ENABLED (known gap)

**Plain statement:** in this lab the `APP.SVRCONN` channel has no `SSLCIPH`.
Application traffic and the app password between the bridge and `mq` travel
unencrypted over the Docker bridge network and loopback. The listener is not
reachable from outside the host by default, which is the only mitigation. Do
**not** open 1414 to a network with this configuration.

Steps to enable (not done here, not tested):

1. Create a key repository (`kdb`/PKCS12) for QM1 with a server certificate
   (from your CA; self-signed only for a lab). In the IBM container set the
   keystore via `MQ_TLS_KEYSTORE` and `MQ_TLS_PASSPHRASE` (mount from a
   secret, not from the repo) and `MQ_TLS_KEYSTORE` path.
2. In `docker/mqsc/20-eventbridge.mqsc` add to the channel:
   `ALTER CHANNEL('APP.SVRCONN') CHLTYPE(SVRCONN) SSLCIPH('ANY_TLS12_OR_HIGHER') SSLCAUTH(OPTIONAL)`;
   for mutual TLS use `SSLCAUTH(REQUIRED)` and add a `SSLPEERMAP` CHLAUTH rule
   with a `SSLPEER` distinguished-name filter.
3. Give the bridge the CA certificate and set the client's SSL key repository
   and cipher spec (`ibmmq` `SCO` with `KeyRepository`, `CD.SSLCipherSpec`);
   set `MQ_TLS` settings in `bridge.env`.
4. Set `SSLFIPS`/cipher policy to match [`../../docs/TLS_POLICY.md`](../../docs/TLS_POLICY.md).
5. Only then consider `mq_client_cidrs` for remote clients, and restrict to
   specific CIDRs. Repeat for the web console (9443 already uses HTTPS with a
   self-signed certificate).

## 5. Encryption at rest and in transit (AWS side)

| Item | At rest | In transit |
|---|---|---|
| EBS root volume | Encrypted gp3 (default EBS key). Note that `qm1data` (persistent MQ messages) lives on it | n/a |
| SQS queues | SQS-managed SSE (`sqs_managed_sse_enabled`) | TLS enforced by queue policy |
| Bundle bucket | SSE-S3 (AES256), public access blocked | TLS enforced by bucket policy |
| Secrets Manager | AWS-managed key `aws/secretsmanager` | TLS (API) |
| EventBridge bus | Platform CMK if configured on the bus | TLS (API) |
| MQ channel | MQ persistent messages are on the EBS volume; no MQ-level encryption | **Plaintext (gap, §4)** |

The queues use SQS-managed SSE rather than the platform CMK. If the platform
policy demands the CMK everywhere, switch the queues to `kms_master_key_id`
and grant `events.amazonaws.com` `kms:GenerateDataKey` and `kms:Decrypt` in the
key policy (otherwise the rule cannot deliver).

## 6. Known risks

- No TLS on the MQ channel (above); single host, no HA.
- Developer MQ image: licensed for development/test only; keep the tag pinned (`10.0.0.5-r2`).
- Anyone with SSM access to the host can read `.env` and `docker inspect`.
- `recovery_window_in_days = 0`: deleting the secret is immediate and irreversible.
- Bridge failures that are not poison messages can still pile up in MQ; alarms
  for `ORDERS.DLQ` depth and `eb-mq-outbound-dlq` are **not** created by this stack.
- No CloudWatch Logs agent: bridge logs live in the Docker `json-file` driver
  (10 MB x 5) on the host and vanish with the instance.
- The web console is HTTPS with a self-signed certificate and reachable only
  from the host (SSM port-forward) unless you open `console_cidrs`.
